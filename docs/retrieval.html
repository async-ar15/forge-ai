Retrieval & Cache

Semantic Caching and RAG Orchestration

Hybrid Retrieval Strategy

To aggressively cut costs, ForgeAI tries to avoid running a full LLM inference whenever possible. It does this by leveraging a tiered retrieval system backed by Redis (Semantic Caching) and Qdrant (Vector Database).

The Retrieval Flow

sequenceDiagram participant Gateway participant Policy participant Redis as Redis (Bloom + Cache) participant Qdrant as Qdrant (Vector DB) participant LLM as Execution Engine Gateway->>Policy: Request (Extracts cache_hit_prob from Bloom Filter) Policy->>Gateway: Action (e.g. CACHE_ONLY) Gateway->>Redis: Check exact / semantic match alt Cache Hit Redis-->>Gateway: Return cached response (0 inference cost) else Cache Miss Gateway->>Qdrant: Fetch context chunks (RAG) Qdrant-->>Gateway: Return context Gateway->>LLM: Execute with Context LLM-->>Gateway: Return generated response Gateway->>Redis: Store response in Semantic Cache end

Retrieval Modes

The Policy Engine dynamically selects the retrieval mode per request:

  • OFF: No retrieval is performed. Useful for simple tasks like "Write a python script".
  • CACHE_ONLY: Only checks Redis. Prevents expensive Vector DB lookups if the request is highly likely to be cached.
  • FULL: Executes a full RAG pipeline, querying Qdrant for document context before sending the prompt to the Execution Engine.
